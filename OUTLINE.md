# Product outline

## Purpose

Make filing documents feel automatic while keeping the filing system understandable.
Paperless Classifier reads an already-consumed document, chooses from the user's
existing taxonomy, and records what it would change. Unclear documents have an
explicit place to wait for review.

The initial audience is a personal Paperless-ngx installation with an established
collection of tags and document types. The application should remain usable by
other Paperless users without hardcoded personal categories or infrastructure.

## First release

| Capability | Behavior |
| --- | --- |
| Document type | Choose one existing type, or abstain when none fits. |
| Tags | Evaluate multiple existing tags independently; propose additions. |
| Review queue | Show current and proposed metadata, uncertainty, and a Paperless link. |
| Manual review | Accept, edit, reject, or defer each proposal. |
| Automatic mode | Apply eligible changes under a versioned, evaluated policy. |
| History | Record decisions, actual changes, failures, and reviewer corrections. |
| Intake | Process explicit document IDs first, then an opt-in queue tag. |

Existing tags are preserved. An existing document type may be shown as a disputed
classification, but changing it requires review in the first release. Empty
document types can eventually be filled automatically. Operational tags, such as
inbox and processing markers, are excluded from the classification vocabulary.

Correspondent matching is a follow-up: it adds candidate-selection and identity
ambiguity that are unnecessary for proving document types and tags.

## Review experience

The landing page is the queue. Each item shows a document title, proposed additions,
the proposed type, and a plain-language status such as "Ready to review" or
"OCR text missing." Opening it shows:

- Current metadata alongside proposed changes.
- A bounded OCR excerpt and a link to the full document in Paperless.
- Per-field model probabilities and the policy reason for review or application.
- Controls to accept, edit using the existing taxonomy, reject, or defer.

Reason text comes from application rules: for example, "Existing type differs"
or "Tag probability is below the automatic threshold." It does not pretend to
be an explanation generated by Jev. Technical run details belong in an expandable
history view, not in the main filing flow.

## Relationship to existing tools

Paperless-ngx already supports rule-based and learned matching. Keep those as a
baseline, and measure whether this classifier improves the hard cases. Its
[matching documentation](https://github.com/paperless-ngx/paperless-ngx/blob/main/docs/advanced_usage.md#automatic-matching)
describes the existing capability.

Paperless-GPT can continue providing OCR or title generation where desired.
Classification ownership must be explicit so two services do not keep rewriting
the same metadata. The homelab's current `needs-tags` proposal/apply workflow
remains responsible for new-vocabulary suggestions during the initial pilot.

## Deliberate scope limits

The first release does not generate titles, create tags or correspondents, perform
OCR, change document files, extract arbitrary fields, or offer document chat.
It also does not retrain Jev from corrections. Corrections form a local evaluation
set and can improve taxonomy descriptions and thresholds in later policy versions.

## Success criteria

- A selected batch can be classified and reviewed without changing Paperless.
- Every proposed metadata value maps to a current, permitted Paperless object.
- Reprocessing unchanged inputs reuses the proposal instead of paying again.
- Applying a proposal preserves unrelated metadata and can reconcile interrupted work.
- Accuracy, abstention, automatic coverage, latency, and cost are measured together.
- Review takes less effort than filing the same documents manually.

An initial evaluation target is at least 98% precision among proposed automatic
tag additions and type assignments, reported separately with denominators and
uncertainty. This is a target, not a claim. A small pilot cannot establish that
rate reliably; categories with too few examples stay in review mode.

## Follow-up opportunities

1. Correspondent selection from existing entries, with an unknown option.
2. A separate "action requested" assessment for explicit obligations in document text.
3. Evaluation against a local model on Spark.
4. Better handling of large taxonomies and long documents.
5. Proposed new vocabulary in a separate review flow.
